在三种语言中实现该算法的运行性能差异显著：

5. 循环分块（Loop Blocking / Tiling）

思想

将矩阵拆分为多个小块，使得每块可完全装入缓存，从而减少主存访问次数。

未分块：

  • 每次写入整行 C，缓存不断被替换。
  • 访问内存约 128 MiB。

分块后（如 64×64）：

  • 每次处理一个小块；
  • 访问内存仅约 4 MiB。

优点

  • 提高缓存命中率；
  • 显著提升内存带宽利用率；
  • 是矩阵乘法性能优化的核心手段。

6. 多级缓存优化 + 向量化

  • 二级分块：针对 L1/L2/L3 缓存的不同容量设计不同 block size；

  • SIMD 向量化：使用 AVX/AVX2/AVX-512 指令；

  • 对 4096×4096 矩阵乘法，性能可提升 超过五万倍。

7. 思考与实践方向

  • 何时循环交换反而无效或降低性能？
  • 并行线程数增加是否总是提高性能？
  • 如何确定最优分块大小？
  • 使用 AVX-512 是否一定快于 AVX2？
  • 能否建立性能与参数（block size、线程数、cache）的数学模型？

一、基准评测的意义

基准评测（Benchmarking）用于：

  • 量化系统性能差异
  • 比较不同硬件/软件实现
  • 指导优化与选型

类型 说明 示例

  • 43个C/C++/Fortran程序；

    • Speed：单实例可多线程；
    • Rate：多实例单线程；

  • 输出指标：

    • 执行时间；

四、基准评测策略

策略类型 定义 示例
固定计算量 任务量固定，测执行时间 SPECspeed
固定时间 时间固定，测完成度 SLALOM
可变计算与时间 同时考虑质量与速度 HINT

五、两条经典定律

阿姆达尔定律（Amdahl’s Law）

当程序中可并行部分占比 ( p )，使用 ( n ) 个处理器时：
[
Speedup = \frac{1}{(1-p) + \frac{p}{n}}
]
限制：串行部分越大，整体加速越受限。

古斯塔夫森定律（Gustafson’s Law）

若问题规模可随处理器数扩展：
[
Speedup \approx p
]
启示：应扩大工作负载以充分利用资源。

六、小结

  • 基准评测提供了标准化性能比较基础；
  • 选择基准应贴近真实负载且结果可复现；
  • 固定计算、固定时间、可变计算三种策略适用于不同场景；
  • 阿姆达尔定律体现上限，古斯塔夫森定律体现扩展潜力。

二、不同语言实现的性能差异

同样的矩阵乘法，用不同语言实现，性能差距巨大。

语言 执行方式 性能特点
Python 解释执行 每一步都经过解释器和对象系统，开销大
Java 即时编译（JIT） 热点代码会在运行时自动优化
C 直接编译为机器码 执行最接近硬件，效率最高

为什么会有性能差异？

  • Python 慢在解释器和对象模型
    每次加法、数组访问都要经过类型检查、函数调用和对象创建。
    循环次数一多，解释器开销远超计算本身。
  • C 语言快在直接操作内存
    编译后是纯机器指令，操作寄存器和内存地址，不需要类型判断或函数调度。
  • Java 介于两者之间
    程序先以字节码运行，虚拟机会监控热点代码，并在运行中把它即时编译（JIT）成高效机器码，自动做循环展开、函数内联等优化。
    因此在不开优化的 C（-O0）对比下，Java 反而可能更快。

三、循环优化

1. 循环交换（Loop Interchange）

循环的执行顺序会影响内存访问的局部性。由于数组在内存中以行主序（Row-major order）存储，若访问顺序与存储顺序一致，可以显著提高缓存命中率。循环交换是把多层嵌套循环的顺序调换，以改变内存访问顺序，从而提高缓存命中率。

2. 编译器优化级别

GCC 提供多种优化选项：

参数 含义
-O0 无优化（调试模式）
-O1 基础优化
-O2 启用主流优化（推荐默认）
-O3 激进优化，包含循环展开与向量化

在开启 -O3 后，C 实现的性能可提升数十倍。

3. 并行化优化

OpenMP 并行化
OpenMP 是 C/C++ 的并行编程接口，它通过编译器指令（#pragma）能让循环并行执行。
多核 CPU 可以通过 OpenMP 指令快速实现循环并行：

#pragma omp parallel for
告诉编译器把接下来的这个 for 循环的迭代分给多个线程去同时执行。
每个线程都会处理不同的 i 值（外层循环的不同部分）。
schedule(static)
控制任务（循环迭代）如何分配给线程：

  • static：编译时平均划分，比如 8 核 CPU，每核分到 n/8 行
  • dynamic：运行时动态分配，适合各迭代计算量不均的情况
  • guided：动态分配，但逐渐减小块大小，常用于负载不均
    对矩阵乘法这种负载均匀的任务，static 性能最好。
    shared(A, B, C)
    声明所有线程共享同一份矩阵数据。
    但每个线程只负责写自己那一块 C[i][j]，不会产生冲突。

一般经验
优先对最外层循环并行化，每个线程计算一整行 C[i][*]，数据独立、缓存命中率高、无写冲突。

4. 循环分块

将大矩阵拆成多个小块，让每个小块能完全放入 CPU 缓存，从而减少主存访问、提升缓存命中率。

未分块：

  • 一次写整行 C，频繁加载/替换缓存；
  • 大量重复访存，约需 128 MiB 内存带宽。

分块后（block = 64）：

  • 每次仅处理 64×64 的小块；
  • 同一块数据在缓存中被多次复用，访存量降至约 4 MiB。

分块大小的选择

块太大：超出缓存，频繁失效；
块太小：循环开销过大。

循环优化与数据依赖分析

说明：本文基于课堂笔记与个人理解整理，所有内容仅用于学习交流。

一、数据依赖类型

True dependence / RAW
先写后读：读到的值必须是那次写产生的，所以必须保持写在前、读在后。

Anti-dependence / WAR
先读后写：后面的写不能跑到前面的读之前去，否则把本该被读到的旧值改掉了。

这类依赖是名字引起的：如果把第二个 x 改名为别的临时变量，约束就没了。

Output dependence / WAW
写依赖写：两次写同一个位置，先后顺序要保持，否则最终值改变。

它同样是名字引起的，改名能消除。

Input dependence / RAR
读依赖读：两次读同一位置，无顺序约束，随便换序都对结果没影响。

动态数据依赖（Dynamic Data Dependence）
实际执行时两个具体操作是否冲突。

静态数据依赖（Static Data Dependence）
编译器在代码层面推断可能存在冲突（只要有一种迭代组合能导致冲突，就认为有依赖）。

二、循环并行性分析

存在跨迭代的数据依赖（loop-carried dependence），循环不是 DOALL（DO ALL iterations in parallel）。
不存在跨迭代的数据依赖，循环是 DOALL，可完全并行。

Distance Vector（距离向量）
定义为目标迭代 (It) 与源迭代 (Is) 的差值，表示数据依赖跨了多少次迭代。
比如，如果 i=5 的迭代依赖 i=4 的结果，那么 d = 1。

Direction Vector（方向向量）
定义为描述依赖关系在迭代空间的相对方向。
对于从 Is → It 的依赖，方向向量是一组符号（每个循环层次一个符号）：
< 表示目标迭代在源迭代之后（It > Is）
= 表示同一次迭代（It = Is）
> 表示目标迭代在源迭代之前（It < Is）
* 表示不确定

迭代空间 (Iteration Space)：嵌套循环用多维坐标表示。
执行顺序：词典序 (lexicographic order)。

编译器在编译时并不知道 n 的具体值，因此无法判断 a[i] 和 a[n] 是否访问同一位置。

数据依赖分析的适用范围
只分析那些循环边界和数组下标是变量的整数线性函数的情况，即循环控制变量和数组访问形式必须是线性的，形如 a*i + b*j + c，其中 a,b,c 为常数。

数据依赖存在的条件

  • 循环变量范围合法：读操作与写操作的迭代索引都必须处于循环允许的范围内。
  • 读写访问同一存储位置：当某次写操作和某次读操作访问的是同一个数组元素时，就存在数据依赖。
  • 忽略非仿射（non-affine）关系：不考虑像 ( i1 * i1 ) 这样的非线性项，因为它超出了线性数据依赖分析的处理范围。

近似测试 (Inexact Tests)

示例方法：

  • GCD Test：通过最大公约数判断线性丢番图方程是否有解。
  • Banerjee Test：通过上下界约束求近似结论。可能过于保守。

可能的两种结果：

  • No → 无依赖
    表示可以确定不存在数据依赖。
  • Don’t know → 假设存在解 → 有依赖（保守处理）
    如果测试无法确定是否存在依赖，则编译器会保守地认为存在依赖，以避免出错。

GCD 测试
在循环并行化中，GCD（Greatest Common Divisor）测试是一种常用的快速数据依赖检测方法。
它通过判断数组下标等式是否有整数解来推测不同迭代间是否存在数据依赖。

示例：

写访问下标：
$$
\text{Write: } 3i_w + 1
$$
读访问下标：
$$
\text{Read: } 2i_r + 5
$$
要访问同一位置，就需要满足：
$$
3i_w + 1 = 2i_r + 5
$$
整理为标准形式：
$$
3i_w - 2i_r = 4
$$

引入 GCD 理论：
设方程：
$$
a_1x_1 + a_2x_2 = c
$$
若想让它在整数范围内有解，充要条件是：
$$
\mathrm{gcd}(a_1, a_2) \mid c
$$
当且仅当最大公约数能整除常数项时，方程存在整数解。

应用于例子：
$$
3i_w - 2i_r = 4
$$
$$
\mathrm{gcd}(3, -2) = 1
$$
因为 $1$ 可以整除 $4$，所以方程存在整数解。
即存在某些 $(i_w, i_r)$ 能同时访问同一个数组元素。
这说明可能存在数据依赖，但还要检查：这些解是否落在循环范围内（$1 \le i \le 40$）。如果超出范围，则依赖无效。

欧几里得算法（Euclidean Algorithm）
GCD 通常通过欧几里得算法计算。
算法步骤：

  1. 设 $(a > b)$，两者为正整数
  2. 计算余数：
    $$
    c = a \bmod b
    $$
  3. 若 $c = 0$，则：
    $$
    \mathrm{gcd}(a, b) = b
    $$
  4. 否则递归：
    $$
    \mathrm{gcd}(a, b) = \mathrm{gcd}(b, c)
    $$

Banerjee 测试简介
Banerjee’s Test 是一种循环依赖分析方法，在 GCD 测试的基础上进一步考虑了循环变量的上下界。

Banerjee 测试通过给方程两边加上上下界限制：
$$
L \le A_1i_w + A_2i_r - C \le U
$$
其中

  • $L$ 与 $U$ 由循环上下界计算得到，
  • 如果常数项不在 $[L, U]$ 区间内，则说明没有合法解，也就不存在依赖。

精确方法 (Exact Analysis)

  • Fourier-Motzkin Elimination：线性不等式消元。
  • Omega Test：判断整数解是否存在，适合编译器依赖分析。

五、Affine Transform Theory

目标：统一程序变换（如循环交换、循环分块、局部性优化）。
迭代空间：d 维循环 → d 维空间。
数组访问：映射为仿射函数。
处理器空间：将迭代分配到虚拟或物理处理器。
仿射变换：循环交换、嵌套重排，提升数据局部性与并行度。

六、循环优化实例

  • Locality Optimization：局部性优化
    空间局部性：内层循环按内存连续方向走

  • Loop Interchange：循环交换
    把循环层次对调：for i { for j { … } } ↔ for j { for i { … } }。

LevelDB WAL 日志恢复与内存管理解析

在学习和阅读 LevelDB 源码的过程中，我被分配的任务是分析 WAL（Write-Ahead Log）日志恢复流程以及 Arena 内存分配器的实现。本篇文章记录了相关源码流程解析和个人理解，适合作为入门笔记与代码讲解资料。

1. WAL 日志恢复流程

LevelDB 为了保证数据的 崩溃恢复能力，在写入 MemTable 之前，会先将更新写入 WAL 文件。当数据库重启时，需要读取并恢复 WAL 文件中的数据。

核心函数：DBImpl::RecoverLogFile

1.1 整体流程

  1. 打开并读取指定的 WAL 文件；
  2. 使用 log::Reader 顺序读取日志中的 record；
  3. 将记录解析为 WriteBatch；
  4. 应用到 MemTable；
  5. 如果 MemTable 达到阈值，则触发转储（flush）。

1.2 关键代码路径

  • DBImpl::RecoverLogFile
    遍历 WAL 文件，逐条恢复 record。

  • log::Reader::ReadRecord
    负责按 record 边界读取完整日志。日志可能跨 block，因此需要拼接。

  • log::Reader::ReadPhysicalRecord
    从底层文件读取物理块（通常 32KB），并检查校验和（CRC），保证数据正确性。

    每次从磁盘读取的数据量：32KB block。

2. WAL Reader 细节

LevelDB 的 WAL 采用 定长 block + record 切分 格式。

  • 每个 block 大小：32KB
  • record 可能跨 block，需要额外处理拼接
  • 每个 record header 包含：
    • CRC 校验
    • length（记录长度）
    • type（FULL, FIRST, MIDDLE, LAST）

log::Reader::ReadRecord 会处理 record 边界，确保最终拼接成一个完整的用户写入。

3. 内存管理 Arena

在恢复 WAL 并写入 MemTable 时，内存分配是频繁的操作。LevelDB 为此设计了 Arena 分配器。

3.1 设计目的

  • 避免频繁调用系统 malloc，减少开销；
  • 提供 顺序分配 的内存模型，适合 MemTable 这样的只增不删的数据结构；
  • 简化释放逻辑（整个 Arena 一次性销毁）。

3.2 Arena 的实现

  • 内部维护一组连续的内存块（block）；
  • Allocate：从当前 block 划分内存；若不足，则新申请一个更大的 block；
  • AllocateAligned：保证对齐分配（适合指针、整数等对齐要求）；
  • 析构时：统一释放所有 block，无需逐一 free。

3.3 内存回收

由于 Arena 只做分配不做单独回收，因此 删除 MemTable = 回收整个 Arena。这种批量回收大大简化了逻辑。

4. 总结

  • WAL 日志恢复：
    LevelDB 在启动时会遍历 WAL 文件，通过 log::Reader 重放写入，保证崩溃恢复的一致性。

  • 日志读取：
    WAL 使用 32KB block，支持跨 block record，利用 CRC 保证数据完整性。

  • Arena 内存分配器：
    通过批量分配和一次性释放，避免了频繁 malloc/free 的开销，简化了内存管理逻辑。

5. 学习收获

  • 通过阅读 DBImpl::RecoverLogFile 与 Arena 源码，进一步理解了存储引擎在 持久化与内存管理 上的取舍。
  • WAL + MemTable 的设计使 LevelDB 在崩溃恢复与写入性能之间取得了良好平衡。
  • Arena 的思想也值得在其他系统设计中借鉴，适合 高频分配、低碎片容忍度 的场景。
